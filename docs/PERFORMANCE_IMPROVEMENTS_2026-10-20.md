# Performance improvements (2026-10-20)

本轮开始前已同步远端 `main`，基线为
`adb06489831cf2f78f50790c25eb7d0ae0c2c762`。范围为 S6、T8、T7、T10、
C10、K1、K3、K4。现有 Worker、Wasm、GPU 预热及轨迹预取继续开启。

## 实现与正确性边界

| 项目 | 改动 | 保留的行为 |
| --- | --- | --- |
| S6 | 首次打开使用启动时的结构 Worker；成功换源后准备一个备用结构 Worker 和解析通道。预热受共享 CPU 配额约束。 | 候选源先解析、成功后提交；失败和取消保留旧源。备用预热失败不能推翻已成功的提交，崩溃后端会清理并按需重建。 |
| T8 | gzip 解压字节块直接进入轨迹索引器；完整帧使用 Blob 范围切片，首帧可在尾部解压完成前返回。 | 不显示不完整原子行，不再二次读取完整解压文件建立索引；取消关闭流，损坏尾部报告索引错误并保留已显示的完整帧。解压后的 Blob 空间仍然需要。 |
| T7 | 有界缓存上一组复制 ID，精确比较源 ID 值、类型、顺序和复制次数；后续 Worker 回复可用请求对应的 token 代替完整字符串数组。缓存不可变 ID 的体积估计。 | 重新排序、原地修改、源切换和重复次数变化均失效；并发回复各自使用请求保留的引用，取消不会复活旧源缓存。 |
| T10 | 在解析器已有坐标写入/转换循环内生成类型计数、首次出现顺序和坐标范围；渲染、图例、统计和类型控件复用摘要。平滑和复制重新生成。 | 使用最终 Float32 坐标的范围；摘要记录数组别名和 revision，数组替换自动失效。公开 renderer setter 对任意可变输入仍重新扫描。 |
| C10 | 周期初始平面在 resident context 中复用；面 CSR 使用可增长 typed buffers；内部三次消息传递使用整数拓扑 ID 和唯一标签表。 | 公共结果仍提供每原子的原有字符串；面、邻居、统计和标签顺序保持一致。已 resident 的 Voronoi 消息也省去重复类型和索引输入。 |
| K1 | 已取得根节点的归并直接复用根，减少并查集的重复查询。无稳定收益的 generation 标记方案已撤回。 | 边遍历、权重相加、同值排序、取向累加、阈值与晶粒编号保持原顺序，不增加每节点的标记数组。 |
| K3 | 少量均匀采样只提供候选配位众数；同一邻居遍历同时计算完整直方图和候选张量。同一不可变快照和 cutoff 可复用经全量验证的众数。 | 最终众数由全量直方图决定；候选不符或内存导致分区变化时回退。低置信样本直接使用原配位循环，保留旧指标计算顺序。 |
| K4 | DXA 在每个 BFS 顶点取出时缓存其不变的晶格坐标、变换矩阵和下一层深度，避免每条边重复读取。串行和线程版 Wasm 同步重建。 | 边访问、浮点表达式、visited 状态、Burgers 回路、结点和搜索顺序保持不变；未跳过空网络的追踪。 |

T10 中“非隔离 Worker 每帧只拷贝一次”的基础复用在基线已经存在：页面
保留一个快照，每个需要该帧的 Worker 首次上传一份，后续块和重复分析复用。
没有 SharedArrayBuffer 时各 Worker 仍需私有缓冲区，本轮不宣称实现多 Worker
零拷贝。T7 保持现有字符串 ID 的公开格式，没有改成新的用户可见 ID 表示。

## 测量方法

本轮使用 Node.js 24.19.0、4 核 CPU 配额的云环境和 Chromium/SwiftShader。
基线由上述提交的 `git archive` 建立，未创建额外 worktree。正式测量逐项独占
执行，不与编译、其他基准或全套测试并行；旧版与新版交错运行并保留原始样本。
每个基准先检查完整科学数组、元数据或稳定摘要，时间不等价于物理 GPU 性能。

可复现入口：

```bash
npm run benchmark:source-loading -- --baseline=/path/to/baseline
npm run benchmark:replication-ids -- --baseline /path/to/baseline --repetitions 5
npm run benchmark:replication-cold -- --baseline /path/to/baseline --repetitions 5
npm run benchmark:frame-summary -- --baseline=/path/to/baseline --atoms=1000000 --repeats=5 --warmup=2
npm run benchmark:voronoi-overhead -- --baseline /path/to/baseline --repetitions 7
node scripts/benchmark-grains-shear.mjs /path/to/baseline 30 5 4 all
npm run benchmark:dxa-tracing -- --baseline-ref adb0648 --kernel both --repetitions 3
```

具体参数以各原始 JSON 中的命令、样本和运行条件为准。解析摘要测量包含增加的
解析成本、传输和显示准备，避免把转移到 Worker 的工作当作消失。Voronoi 的
内部标签传输微基准与完整 Worker 计算分开；局部剪切同时测正常命中和回退。

T7 的驻留成本也有记录：该样本的 Worker 保留约 61.36 MB ID 布局和
0.48 MB 源 ID 快照；页面的多个复制帧共享生成的 ID 数组。以上稳态结果不代表
首次构造、源 ID 变化或复制次数变化的耗时。
单独的 5 次换源测量中，完整 Worker 往返为 553.43 → 573.09 ms（约增加
3.6%，样本波动较大），直接构造为 287.12 → 292.44 ms。冷路径不宣称提速。
更换布局时，若旧缓存加新分配会超过复制预算，会释放旧缓存持有的引用；
已经发出的请求仍持有各自正确的不可变 ID，不会因淘汰而改用别的布局。
编码源 ID 时也逐项检查剩余预算，超限立即拒绝，不先保留整组转义字符串。

T10 把一部分工作移入解析：dump 解析本身为 182.55 → 193.78 ms，XYZ 为
221.44 → 230.48 ms。完整首次准备仍更快，但不能仅引用缓存帧数字来描述冷加载。

S6 额外保留一个备用结构 Worker 和一条解析通道，不在备用后端保留旧源的大数组。
T8 将待封装解压块限制在约 8 MiB，另有当前平台块和最长文本行；随机访问所需的
已解压 Blob 总空间仍随轨迹大小增长，不能将其描述为整条轨迹恒定内存。
该 gzip 基准的 Blob 读取量从 21,978,276 降为 708,976 字节，恰好减少整份
21,269,300 字节解压文件的二次索引读取；所有帧输入字节和首末帧科学结果一致。

K4 是有明确范围的改进，尚未完成整个串行阶段重构。HEA、Fe、NiGB 在两个
内核中的完整科学结果 SHA-256 均与基线一致；独立线程回归另行覆盖四线程路径。
Fe 的追踪本来只有约 0.1 ms，因此不宣称该样本提速。NiGB 的串行完整提取为
13,491.25 → 12,578.81 ms，线程版为 12,513.88 → 12,370.01 ms，但这些总耗时
包含未修改阶段的波动。最初的 BFS frontier 剪枝候选没有可靠收益，已撤回，
[实验记录](benchmarks/dxa-tracing-frontier-rejected-2026-10-20.json)保留供复核。
周期 Delaunay、弹性分类、紧凑边表示和依赖顺序严格的结点/拓扑提交仍列入
[后续工作](DXA_CPU_PROFILE.md#prioritized-further-work)。

K1 的最终方案只复用已知并查集根，不增加图标记数组。独立于计时的计数中，
automatic 的 `find()` 调用为 431,984 → 215,992，MST 为
1,886,376 → 1,454,392；邻接清空遍历仍为原来的 1,889,307 次。
合成四取向分区样本的完整模型、分割及两个缺陷夹具均精确一致。
减少调用次数不能等同于稳定的端到端提速，因此 K1 的进一步串行优化仍在待办中。

K3 使用三次完整预热后交错测量；私有模式五次、共享模式三次。表中的重复帧
结果与新快照结果分开：后者在每次计时前改变坐标，重新生成快照与索引，
不会沿用上一帧经验证的众数。所有科学字段均逐元素按 `Object.is` 比较。
低置信 pilot 直接使用原配位循环；初次候选不符、任意分片放弃，或迁移到
不同候选模式的 Worker 时，全量回退保留原来的浮点归约分区和顺序。
误导 pilot 的新帧仍可能更慢，这一限制和后续工作保留在 [TODO](TODO.md)。
